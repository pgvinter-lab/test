# Mailbox v3 and Bridge 2.0 Prerequisite Independent Review Request

## Context for Reviewer (Claude)

This is an independent review request for the Mailbox v3 candidate and the proposed Capability Catalog (ADR 0010) prerequisite for Bridge 2.0. You are acting as the independent semantic reviewer for AGY's execution. Do not trust AGY's summary. You must re-run required tests and semantically review all staged and intended v3 files, the proposed ADR 0010, and the proposed decision-register entry.

You must answer these 12 numbered questions in a new document: `docs/reviews/MAILBOX_V3_CLAUDE_REVIEW.md`. Distinguish between defects (code bugs, test failures, invariant violations) and policy disagreements (architectural choices you would make differently). Preserve every disagreement. Report exact commands you ran and their exit codes. Finally, state whether any material finding remains unresolved.

## The 12 Review Questions

### 1. v2-to-v3 Migration Exclusivity and Nonterminal Handling
Analyze `src/v2/mailbox/migrate.ts` and `src/v2/mailbox/migrate-web.ts`. Does the migration explicitly require an exclusive idle database window? Does it correctly abort or handle cases where messages are currently in a nonterminal state (e.g., `preparing`, `queued`, `claimed`, `dispatching`, `sent`)? Ensure it does not forcefully mutate active in-flight messages using raw SQL, which could cause state corruption or dropped messages.

### 2. Digest-Manifested Backup and Exact Rollback Window
Review the migration backup strategy. Is the backup digest-manifested to ensure cryptographic integrity? Confirm the exact boundaries of the rollback window: it should only exist *inside* the migration command before v3 mutations occur. Once v3 mutation begins or the command completes successfully, rollback is no longer supported via this script.

### 3. Preservation of v1/v2 Rows, Exchange Bytes, Event Chain, and Audit Mirror
Verify that the migration does not alter historical v1 or v2 rows. The exchange bytes (payloads), the event chain, and the audit mirror must remain byte-preserved. The v3 schema must act as an additive layer or superset without mutating historical cryptographic hashes or audit trails.

### 4. Surviving-Writer Fencing Through Required Schema Versions
Check the broker logic (`src/v2/mailbox/broker.ts` and related files). Are surviving v2 writers strictly fenced out? If an old v2 worker attempts to write a message using an outdated schema version, does the system fail closed? It must reject outdated schema writes to protect the integrity of the v3 tables.

### 5. Provider Rules: ChatGPT, Antigravity, generic 'web', historical Gemini only
Confirm the provider enforcement. The system should strictly recognize only `chatgpt`, `antigravity`, and the generic `web` provider for active processing. `gemini` should be treated as historical/read-only. Verify that no new, undocumented providers have slipped in and that these bounds are strictly enforced.

### 6. Exact-origin WEB-node profiles and absence of `<all_urls>`
Examine `integrations/web-nodes/profiles/perplexity.json` and the Chrome extension manifest (`integrations/chrome-mailbox/manifest.json`). The web-node profiles must specify exact origins. Crucially, the extension manifest must NOT request the `<all_urls>` permission. It must operate on a strict, least-privilege origin model.

### 7. Browser-owned Authentication State and Credential Isolation
Review the Chrome extension code (`background.js`, `content.js`). The browser's authentication state (cookies, localStorage, session data) must remain strictly isolated within the browser. At no point should the extension read and transmit this raw authentication state into Git, Google Drive envelopes, or the local SQLite store.

### 8. No-auto-resend, Dispatch Boundary, Uncertainty, Idempotency, and Leases
Verify the behavior of message dispatch. Once a message crosses the dispatch boundary, there must be no automatic resend mechanism. If a message is in an `uncertain` state, it must remain there for manual owner review. Check that idempotency keys and leases are properly respected to prevent duplicate executions.

### 9. Immutable Drive Envelopes plus Readable WEB Output Provenance
Review `src/v2/mailbox/exchange.ts`. Ensure that Google Drive envelopes used for message payloads are immutable. Additionally, verify that the provenance of output generated by WEB nodes is clearly readable and attributable to its exact origin, preventing spoofing or ambiguous execution traces.

### 10. Strict Schemas, Examples, Migration Tests, Installer, and Extension Behavior
Semantically review all v3 schemas located in `contracts/mailbox-v1-draft/v3/schemas/` (`claim`, `config`, `message`, `ready`, `response`, `web-node`) and their corresponding JSON examples. Do these specific schemas strictly define their expected properties and restrict `additionalProperties` appropriately? Review `test/mailbox/migration.test.mjs` and `src/v2/mailbox/install.ts`. Ensure the installer behaves predictably and the tests comprehensively cover migration paths. Ensure no generic un-typed payload wrappers are forced onto these strictly typed envelopes.

### 11. Repository File Completeness, Packaging, and Machine-local Exclusions
Review the candidate's file inventory. Are all 39 intended product files present? Does `npm pack --dry-run` correctly include all required v3 artifacts while explicitly excluding live configuration, tokens, SQLite/WAL files, audit state, browser state, and Drive contents? Verify that machine-local runtime material (e.g., `.codex`, `.agents`) is correctly excluded via `.git/info/exclude`.

### 12. D-021, Live-Cutover Truthfulness, and the Proposed ADR 0010/Caps Decision Boundary
Assess the D-021 launch criteria for truthful reporting. Review the proposed ADR 0010 (`docs/adr/0010-capability-catalog.md`) and the new decision-register entry. Do they correctly frame the capability catalog as a strict control plane (not a proxy) with three definitive authority tables and a non-overridable ordering? Ensure packages 08-13 are explicitly noted as missing and out-of-scope for this job, and verify no implementation for a capability schema is claimed to exist in this patch.

## Supplementary Review Constraints and Expanded Context

The independent review process must act as an adversarial quality gate. The Mailbox v3 candidate is a highly sensitive infrastructure layer that bridges native operating system capabilities with isolated, un-trusted browser environments. If a single invariant is violated, Claude must mark the review as failed and explicitly outline the defect. AGY relies on this external verification to catch architectural regressions that internal test suites or syntax checks might miss.

For Question 1 (Migration Exclusivity), Claude should inspect the migration scripts for concrete state machine enforcement. If the script attempts to run while the broker is actively polling, or if it encounters messages with states that are in active transit (such as `queued` or `dispatching`) and forcefully alters their status via raw `UPDATE messages SET status='failed'` SQL queries instead of using the API, this must be flagged as a critical defect. The migration script must halt and throw an error, explicitly requiring the system owner to drain or formally terminate those active tasks. The only statuses allowed during a safe schema migration are `completed`, `failed`, `uncertain`, and `expired`.

For Question 6 (Exact-origin), Claude must verify that `host_permissions` in the extension manifest are tightly scoped. If the extension can theoretically execute content scripts on any arbitrary webpage (e.g., by requesting `*://*/*`), it constitutes a severe security vulnerability and an immediate failure condition. The `perplexity.json` profile, as the vanguard example of a generic web node, should only permit injection into the precise `perplexity.ai` domains required for functionality.

For Question 7 (Credential Isolation), Claude should review the message payloads sent from the content script to the background script, and from the background script to the native messaging host. The payloads must contain only the user's intent (the prompt) and the generated response (the inference). Session IDs, OAuth tokens, local storage dumps, or other authentication materials must never be serialized into these payloads or written to the `Bridge Exchange` folder. Bridge 2.0 explicitly operates under a model where the browser completely owns and isolates the authentication state.

For Question 10 (Strict Schemas), Claude should use a JSON schema validator conceptually to ensure that the individual schema definitions (`claim.schema.json`, `config.schema.json`, `message.schema.json`, `ready.schema.json`, `response.schema.json`, and `web-node.schema.json`) correctly and exhaustively enforce the structure of a mailbox payload. Ensure that there are no generic wildcard properties (`additionalProperties: true` without constraint) that would allow an attacker to bypass type checking. The schemas must be strictly tailored to the specific envelopes required by the v3 contract, not a hypothetical catch-all format. 

For Question 12 (ADR 0010 and Caps Decision Boundary), Claude must meticulously verify that AGY did not accidentally claim to have implemented the capability catalog schemas or the routing logic itself. The catalog design proposed in ADR 0010 must reflect the reality of the codebase: the architectural design exists, the control plane concepts are defined (the three authority tables and the cost-tier priority), but the deep package decomposition (Packages 08-13) and the actual database implementation are still pending future work. No live SQLite table creation for capabilities should be present in this specific patch.

This document must be strictly adhered to by the independent reviewer. Any deviation from the numbered list, or failure to explicitly answer a specific question with evidence, invalidates the review. Claude's final output will be placed in `MAILBOX_V3_CLAUDE_REVIEW.md`. AGY will then systematically process that document. If there are any unresolved material findings, the codebase cannot be committed.

The rigorousness of this review is directly tied to the D-021 launch criteria for Bridge 2.0. The five criteria are: no data loss, zero-downtime rollback, backward compatibility, write-fence isolation, and cryptographic integrity. The independent reviewer must evaluate the proposed code changes through the lens of these criteria. For example, if the v3 migration schema lacks the necessary triggers to prevent a v2 worker from successfully writing a malformed record to the database, then write-fence isolation has been breached, and the review must fail. If the backup manifest does not include a cryptographically secure hash of the pre-migration database, then zero-downtime rollback cannot be guaranteed, and the review must fail.

Claude's responsibility is not merely to check for syntax errors or passing unit tests. Claude must evaluate the semantic implications of the architectural choices. While policy disagreements (e.g., "I would have used a different library for schema validation") should be noted but not necessarily block execution, true defects (e.g., "The schema validation allows un-sanitized HTML to pass through the broker") must block the cutover. The distinction between these two categories is vital for maintaining forward momentum without compromising security or data integrity.
